# Tanebi 基盤ドクトリン — 用語定義と OST

> なぜこの文書があるか: 仮説検証の会話は、**用語の定義がずれた瞬間に永遠に噛み合わなくなる**。「問題」「課題」「機会」「仮説」を全員が同じ意味で使うことが、このエンジンの土台である。定義の出典: SPRINT Japan の実運用定義＋ Teresa Torres / Marty Cagan の Continuous Discovery の考え方（書籍 "Continuous Discovery Habits" 参照）。

## 1. 階層 — 問題・課題・リスク・ToDo を混ぜない

```
リスク   ← まだ起きていないが、近い将来問題になり得る確度の高い事象
  ↓
問題     ← すでに起きている、観測可能な事象。ゴールへの取り組みを阻害するもの
  ↓
課題     ← ゴールと現状（問題）のギャップを埋めるための「取り組み」
  ↓
ToDo     ← 課題を解決するために実際に行う、結果を伴う具体的な行動
```

よくある誤り: 「売上が足りない」を機会と呼ぶ（それは自社の**問題**）。「顧客理解を深める」を仮説と呼ぶ（それは**課題**）。「Aさんに電話する」に仮説を要求する（それは**ToDo**）。

## 2. 仮説の定義と必須文型

**仮説**とは、新しく構想したサービスが顧客課題を解決するもの（ソリューション）であるとまだ確かめられていないとき、それを説明する命題である。検証を通じて事実と合致すれば定説となる。

**必須文型（この形で書けないものは仮説と呼ばない）**:

> **［顧客セグメント］は、［顧客課題＝すでにとっている行動］があるので、［解決策］を受け入れてくれるはずだ。**

例（低価格ヘアカット業態の考え方を借りた例文）:

> 「髪を切るだけでいいと考えている多忙な男性は、待ち時間と拘束時間を減らすために予約なしで済む店を選ぶ行動をすでにとっているので、シャンプーやマッサージを省いた10分カット専門のサービスを受け入れてくれるはずだ。」

3つの空欄がそれぞれ果たす役割:
- **顧客セグメント**（主語）: 書けなければ誰にも検証できない。主語の書けない仮説は採用しない
- **顧客課題＝すでにとっている行動**: 仮説の根拠。願望ではなく行動（次節）
- **解決策**: 最小の形で。解決策が2つ以上入るなら仮説を分ける

## 3. 「日常の不」と「顧客の課題」は違う

**顧客の課題**＝「日常の不安や不便を克服・解決するために**すでにとっている行動**」あるいは「目標を達成するためにしている日々の行動」。

- ×「請求書作成が面倒だと感じている」— 感情・日常の不。誰でも言うが、金は動かない
- ○「請求書作成のために毎月末に半日かけて Excel を組み直している」— 行動。時間という支払いがすでに発生している

行動には**すでにコストが払われている**。だから行動に根ざした仮説だけが、支払意思の予測材料になる。

## 4. OST（オポチュニティ・ソリューション・ツリー）— 顧客側の木

```
顧客の成果（顧客が達成したいこと）
  ↓
機会（顧客がすでにとっている行動・不安・不便）  ← インタビュー由来でなければ「機会」と呼ばない
  ↓
解決策
  ↓
実験
```

**機会と呼べるのはインタビュー由来の事実だけ**。記録やAIの推論から生成したものは、どれほど確からしくても「**機会の仮説**」と表記する。この一語の規律が、机上の空論と検証済みの事実の混同——仮説業務で最も高くつく事故——を防ぐ。

## 5. 運用ルール R1〜R6

| # | ルール | なぜ |
|---|---|---|
| R1 | **木を2本に分ける。** 顧客側（OST）と経営側（問題→課題→ToDo）を同じ図に混ぜない。KPI・アクセス解析等の自社指標はすべて経営側 | 自社の数字を顧客の機会と誤認するのが、仮説業務の最頻出事故だから |
| R2 | **機会は顧客のもの。** 「我々は知らない」「我々は測れていない」は機会ではなく自社の**問題** | 主語が自社になった瞬間、顧客検証は自社正当化に変わるから |
| R3 | **インタビュー由来でないものを「機会」と呼ばない。** 机上のものは「機会の仮説」と明記 | 呼び名の規律が認識の規律を作るから |
| R4 | **主語（顧客セグメント）が書けない仮説は採用しない** | 誰に検証するかが決まらない仮説は、原理的に検証できないから |
| R5 | **検証方法（実験）が書けない仮説は採用しない** | 実験のない仮説は意見であり、意見は蓄積しても資産にならないから |
| R6 | **すべてに仮説を立てない。** 運用上の不具合は ToDo であり、仮説を要求しない | 仮説の形式を乱用すると、本物の仮説の価値が薄まるから |

## 6. この定義の由来

この定義体系は、AI が「自社の問題」を「顧客の機会」として提示する誤りを実際に犯した経験から正本化された。**AI が同じ誤りを繰り返すのを止めるには、定義を明文の正本として置き、すべての生成物をそれに従わせる以外に方法がない。** Tanebi を導入するチームは、この文書をそのままチームの用語正本として採用してよい（自社の言葉に合わせて改変する場合も、R1〜R6 の構造は保つことを勧める）。
